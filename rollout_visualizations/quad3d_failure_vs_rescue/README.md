# Quadrotor-3D: baseline failure vs. composition rescue

## Rendering fix in this cut (scale, floor, camera)

Every earlier cut of this directory (and of `quad3d_composition/`, which
shares the same `render_frames` helper) rendered the drone at **5x its true
size** and with **no ground plane** -- the playback DIRECT client loaded only
the drone, so the background was flat white. Both are now fixed in
`visualize_quad3d_composition.render_frames` (reused here, not
reimplemented):

- `DRONE_VISUAL_SCALE = 1.0` -- the real `cf2x.urdf` body.
- `plane.urdf` is now loaded at `GROUND_PLANE_Z = -0.05`, matching what the
  live env loads, giving a floor and a fixed reference for altitude/motion.

Camera retuned empirically for the true-scale body (rendered and inspected by
eye at several distance/pitch/fov combinations first): `CAMERA_DISTANCE =
0.5 m`, `CAMERA_PITCH = -15 deg` (horizon roughly a third of the way down the
frame), `CAMERA_YAW = 45 deg` (unchanged), `CAMERA_FOV = 60 deg` (unchanged).
Full rationale in `quad3d_composition/README.md`'s matching section and in
`visualize_quad3d_composition.py`'s `CAMERA_*` constant comments.

**Only rendering changed.** The physics, the three candidate initial states,
and every simulated outcome (crash ticks, handoff ticks, goal-reached frame)
below are unchanged from the previous cut -- confirmed by the frame/duration
counts matching exactly (572/607/613 frames, 19.1 s/20.2 s/20.4 s).

Three paired videos, each showing the SAME dramatic initial state (166-180
deg initial tilt, i.e. near-full inversion) played through two arms
side-by-side in a single MP4:

- **Left / red banner -- BASELINE**: controller 2 (LQR) alone
  (`rollout_composite(..., ctrl1=None, ...)`). Fails every time by
  construction (see "How these states were picked" below).
- **Right / green banner -- COMPOSITION**: controller 1 (the "flip" policy)
  runs until the state first enters the attitude-only handoff region `G1`,
  then control latches PERMANENTLY to controller 2 (LQR), which flies to the
  goal (`rollout_composite(..., ctrl1=<shipped>, ...)`). Succeeds every time.

This is the composed-ROA gain -- **21.20% (LQR alone) -> 46.36% (composed)**,
**11116/40000 states where composition wins and the baseline loses** -- made
visual instead of tabulated.

## How these states were picked

1. Loaded both paired `eval_states.txt` files (baseline: 27 cols
   `init(13), final(13), ctrl2_success`; composite: 28 cols
   `init(13), final(13), flip_success, ctrl2_success`) and confirmed the
   `init(13)` columns match row-for-row (`np.allclose`).
2. Filtered to the 11116 rows where baseline `ctrl2_success == 0` AND
   composite `ctrl2_success == 1`.
3. Computed each row's initial tilt from its quaternion via the rotation
   matrix (`quad_composition.rollout3d.tilt_from_quat_wxyz`, NEVER Euler
   angles -- see that module's docstring), and sorted descending.
4. The eval datasets were generated with the **75k** controller-1 checkpoint
   (`models/quad3d_ctrl1_selected_prev2.pt`); the **shipped** controller is
   now the **300k** checkpoint (`models/quad3d_ctrl1_selected.pt`, md5
   `e1a6d59afc1b887e4e0c97b89bc63e4a`). So the top-tilt candidates were
   re-verified by actually re-running BOTH arms against the shipped 300k
   checkpoint (not trusting the dataset's stored labels): baseline must still
   fail AND visibly leave the state-space box (a Euclidean `TERMINATION`
   bound violation, not just a goal-tolerance miss), and the composition must
   still reach `G1` and then the goal. The top 3 candidates by tilt (rows
   31023, 12931, 9579; 178.7 deg, 177.6 deg, 176.9 deg) all reproduced on the
   first try -- no candidates had to be discarded, and reproduced again for
   this cut (rendering-only change, same re-verification at render time).

G1 used throughout: `flip_env3d.G_NOM_3D` (tilt_c = 0.175 rad / 10.0 deg,
w_c = 4.0 rad/s) -- the same region controller 1 was trained to reach, fixed
(not calibrated) for the 3D branch.

## Per-pair detail

Camera tracks the drone every frame (retargeted to its current position); the
state space is the closed 3.6 x 3.6 x 2.9 m box (x, y in [-1.8, 1.8] m, z in
[0.1, 3.0] m).

### Pair 0 -- `pair_00/side_by_side.mp4` -- initial tilt 178.7 deg

- **Baseline**: crashes in 26 physics ticks (0.26 s of sim time) -- spins out
  and exceeds the y-velocity bound (`y_dot` = +3.01 m/s vs. the +/-3.0 m/s
  termination bound). Frozen (held) in that out-of-bounds pose from video
  frame 62 onward, captioned "FAILED -- LEFT THE BOX".
- **Composition**: handoff to LQR fires at tick 21 (0.21 s in, video frame
  57) -- controller 1 only needs a fifth of a second to reach `G1` from
  near-full inversion. Full rollout runs 460 ticks (4.6 s sim time) and
  reaches the goal; captioned "SUCCESS -- GOAL REACHED" from video frame 496.
- Video: 572 frames @ 30 fps = 19.1 s (native 100 Hz capture, i.e. ~3.3x slow
  motion throughout, plus a 1.2 s intro hold on the shared start pose and a
  2.5 s outro hold on each side's final pose).

### Pair 1 -- `pair_01/side_by_side.mp4` -- initial tilt 177.6 deg

- **Baseline**: crashes in 49 ticks (0.49 s) -- exceeds the z-velocity bound
  (`z_dot` = -3.06 m/s vs. +/-3.0 m/s), i.e. falls out of the box vertically.
  Frozen from video frame 85, captioned "FAILED -- LEFT THE BOX".
- **Composition**: handoff at tick 25 (0.25 s in, video frame 61). Full
  rollout runs 495 ticks (4.95 s) and reaches the goal; "SUCCESS -- GOAL
  REACHED" from video frame 531.
- Video: 607 frames @ 30 fps = 20.2 s.

### Pair 2 -- `pair_02/side_by_side.mp4` -- initial tilt 176.9 deg

- **Baseline**: crashes in 42 ticks (0.42 s) -- exceeds the y-velocity bound
  (`y_dot` = -3.07 m/s vs. +/-3.0 m/s). Frozen from video frame 78, captioned
  "FAILED -- LEFT THE BOX".
- **Composition**: handoff at tick 21 (0.21 s in, video frame 57). Full
  rollout runs 501 ticks (5.01 s) and reaches the goal; "SUCCESS -- GOAL
  REACHED" from video frame 537.
- Video: 613 frames @ 30 fps = 20.4 s.

All three: baseline fails inside half a second by spinning out through a
velocity bound (never a graceful recovery-then-drift -- a hard, fast tumble
off the edge of the box); composition reaches the attitude-handoff region in
about a fifth of a second and then flies to the goal under LQR over the
following ~4.5 s. Confirmed by inspection of extracted frames at each video's
start, handoff, and end (baseline: visibly tumbled and off-target at the
freeze frame; composition: visibly upright and centred on the goal ring at
the freeze frame) -- the two arms do not look the same at any point after the
first second.

## Format

**Single side-by-side MP4 per pair** (not paired separate clips): baseline on
the left, composition on the right, from the identical initial state, in one
`pair_NN/side_by_side.mp4` file. Both arms are captured at the native 100 Hz
physics tick (no frame-skipping) so frame *i* means the same simulated
instant on both sides -- true lock-step sync, not just "both videos start
together". The shorter arm (always the baseline) is padded with repeats of
its own final pose once its real trajectory ends, so both panels run the same
total length; both open on a frozen 1.2 s of the identical start pose (so the
dramatic tilt is unmissable before anything moves) and close on a frozen
2.5 s of their own outcome. All 1920x1088, h264, 30 fps.

On-screen labelling: a title banner (pair number, shared initial tilt), a
static per-panel arm label, and a live status caption that appears exactly
when that arm's outcome is reached (`FAILED -- LEFT THE BOX` /
`HANDOFF -> CTRL2 (LQR)` / `SUCCESS -- GOAL REACHED`). The composition arm
also carries the existing pipeline's handoff cues from
`visualize_quad3d_composition.render_frames`: the drone's own body colour
switches from black to orange at the handoff frame, plus a magenta marker
bead left at the handoff position in space.

## Verification

- `ffprobe` on all three: valid h264, 1920x1088, 30 fps, 572/607/613 frames
  (19.1 s / 20.2 s / 20.4 s), non-zero duration -- identical frame/duration
  counts to the previous (5x-scale, no-floor) cut, confirming only rendering
  changed.
- Frames extracted at start / mid / handoff / end for each pair and inspected
  visually -- floor now visible with checkerboard perspective, drone reads at
  true scale; baseline visibly crashes and freezes tumbled and off-target;
  composition visibly changes colour at handoff, tracks to the goal ring, and
  freezes upright on it.
- Each candidate's baseline-fails / composition-succeeds outcome was
  re-produced at render time against the SHIPPED controller (the render
  script re-runs both arms and raises if either outcome no longer holds,
  rather than trusting the embedded dataset labels).

## Regenerating

```bash
python3 render_quad3d_failure_vs_rescue.py \
    --output_dir rollout_visualizations/quad3d_failure_vs_rescue
```

The 3 candidate initial states are embedded in `CANDIDATES` at the top of
that script (with provenance comments), so this is self-contained and does
not depend on the `/tmp` scratch files the selection/verification passes
used.

**`--pair_index N`** renders only `CANDIDATES[N]`, merging its sidecar into
any existing `summary.json` rather than overwriting it. Added in this cut
because the floor+shadow render is ~10x more expensive per frame than the
old floor-less render (measured: ~33 ms/frame -> ~330 ms/frame at
1920x1080-per-panel with shadows), which pushed a full 3-pair run past a
single foreground call's wall-clock budget on a contended host -- each pair
was rendered in its own `--pair_index` invocation instead.
